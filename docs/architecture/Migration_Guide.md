## 1. Executive Summary & Migration Philosophy

In **FinTrack Pro**, database schema migrations are managed as code, version-controlled in Git, and executed predictably across environment pipelines using **Prisma Migrate**.

Direct manual schema edits via `psql` or administrative tools are strictly forbidden in non-local environments. Every schema change must pass through the formal migration workflow to guarantee zero data loss, version alignment, and smooth deployment rollouts.

## 3. Step-by-Step Migration Execution Protocols

### 1. Initial Database Baseline Migration
To initialize the enterprise baseline database schema on a fresh PostgreSQL instance:

```bash
# 1. Ensure DATABASE_URL is set in environment
export DATABASE_URL="postgresql://user:pass@localhost:5432/fintrack_db?schema=public"

# 2. Execute baseline migration
npx prisma migrate dev --name init_enterprise_schema

# 3. Seed foundational data
npm run db:seed
```

---

### 2. Incremental Schema Migrations (Developer Workflow)
When modifying a model or adding an index:

1. **Update `prisma/schema.prisma`:** Make declarative model edits.
2. **Validate Schema:** Run `npx prisma validate` to confirm syntactical correctness.
3. **Generate Migration SQL:**
   ```bash
   npx prisma migrate dev --name add_forecast_confidence_index
   ```
4. **Inspect Generated SQL:** Inspect the generated SQL script in `prisma/migrations/<timestamp>_add_forecast_confidence_index/migration.sql` to verify safety.
5. **Commit Migration Directory:** Commit both `schema.prisma` and the newly generated `prisma/migrations/` folder to Git in a single commit.

---

### 3. Production Deployment Migration (`npx prisma migrate deploy`)
In CI/CD production deployment pipelines:

- **Never use `prisma migrate dev` in production.**
- Execute `npx prisma migrate deploy` during pre-deployment container boot. This command executes pending migrations from `prisma/migrations/` atomically without prompting.

```bash
# Production Deployment Command
npx prisma migrate deploy
```

## 4. Emergency Migration Rollback Strategy

PostgreSQL migrations generated by Prisma execute inside DDL transaction blocks. If a migration fails during execution:

1. **Automatic Transaction Rollback:** PostgreSQL rolls back DDL statements within the failed transaction block, leaving the database state intact.
2. **Marking Failed Migrations:** If a migration fails midway due to a lock timeout, resolve the root cause and execute:
   ```bash
   npx prisma migrate resolve --rolled-back "<migration_folder_name>"
   ```
3. **Applying Corrective Migration:** Apply a compensating forward migration (`--name fix_previous_migration_issue`) rather than attempting manual database edits.

---

## 5. Zero-Downtime Migration Guidelines (Expand & Contract Pattern)

For high-availability enterprise environments operating under 99.99% SLA:

1. **Phase 1 (Expand - Non-breaking):** Add new columns as `NULLABLE` or with default values. Deploy application code that writes to both old and new columns.
2. **Phase 2 (Backfill):** Run a background data migration script to populate historic records in the new column.
3. **Phase 3 (Contract):** Deploy code using the new column exclusively, then remove the old column in a subsequent release.
